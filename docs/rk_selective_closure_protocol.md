# Selective parallel RK closures: frozen follow-up protocol

## One candidate, fixed before timing

The previous [broad-gate study](rk_parallel_closure_benchmark.md) motivates a
minimum **32,768 simplices per level**, in addition to the unchanged saturated
face-work estimate (8,192 estimated entries per task, at least two tasks).
The size test runs before the work-estimation scan or task scratch allocation.
It uses one level's immutable size, not the whole complex or sum of active levels.
The threshold is inclusive. This is a data-informed heuristic, not a theoretical
break-even bound. Do not retune it after observing this experiment.

`parallel_closure_preparation` remains false by default. When explicitly enabled,
`parallel_closure_min_level_size` defaults to 32768; setting it to zero reproduces
the previous broad gate. Traversal, merging, gradient ordering, per-task work
threshold, executor and all other algorithm phases are unchanged.

Tests cover zero/default/equal-to-size/size-plus-one thresholds, 1/2/4/8 workers,
on/off, ordinary/coarse/detailed execution, single and concurrent levels, eager
cache agreement, unchanged work counts, and existing exception-draining controls.
The profiling driver explicitly enables the same feature as `run`/`rk_plain`;
it must not silently profile the default-disabled library policy.

## Comparisons and inputs

Baseline: `12ee94a`, with closure parallelism **disabled**, its library default.
Use `--baseline-closure-serial`; the old runner's baseline `run` would enable the
broad prototype and answer a different question. Candidate-on uses the new
selective gate; candidate-off disables closure parallelism. Both candidate modes
share one executable and resident process. Old/new off measures version/context
effects; on/off is the primary feature comparison. No direct current-session
broad-on comparison is claimed; that experiment remains separately reported.

Keep all six previous inputs: 7D/side-2 seeds 3 and 1, 6D/side-2 seeds 4 and 1,
volume-32 and volume-16 seed 0. Add 7D/side-2 seeds **6 and 7**, generated by the
existing deterministic `grid_input` function, before inspecting their level
profiles or timings. They are new to this closure experiment, not an independent
representative corpus. Record which levels actually dispatch; do not infer task
execution merely from size eligibility. Never discard an unfavourable new seed.

Freeze sources/runner/protocol in a clean commit. Use the same current ordinary-only
driver with frozen old/new headers, Clang `-std=c++17 -O3 -DNDEBUG -pthread`.
Retain binaries, header/source/input hashes, no-trace symbol evidence and exact
ordered sequential reference dumps. Compile and run correctness/sanitizer checks
before timing; do not overlap builds/tests/profiling with performance sessions.
Retain host load averages, but do not treat them as a correction for interference.

At 1 and 8 workers, each input has two fresh process pairs per session, two
warmups per mode, six blocks of six repetitions, all six mode and algorithm
permutations. A second session reverses input/worker and pair schedules. This
gives four independent pair estimates per configuration and 10,368 timed gradient
calls per session. Keep baseline and candidate launch order balanced.

Loading/native construction are separate observations. Time complete gradients
from a finalized complex in memory: fresh builder, all algorithm-specific
preparation, pool, local work, replay and in-method cleanup. Reference checking
and returned-object destruction are outside timing. No persistence or TTK rerun.
F-Max/PLS are unchanged controls, not a replacement paper-facing ranking.

## Acceptance and reporting

Primary target: retain a repeatable useful benefit on 7D seed 3 at eight workers
(median on/off < 0.95, benefit in both sessions). Previously penalized smaller
levels must dispatch zero closure tasks, and their timing controls must remain
visible even if they still vary. Flag any control or added seed with median
on/off > 1.05 and slower estimates in both sessions; do not silently label it
noise. Also retain old/new off and sequential warnings. Gated-out or one-worker
on/off differences cannot be attributed to parallel closure work.

Independently recompute all 1,728 phase summaries from raw repetitions. Show
each process pair and its conditional 95% block-bootstrap interval. Across four
pairs show median and observed range, not a pooled confidence interval. Report
absolute gradient times and separate builder/kernel/total ratios in the appendix.
Validate critical counts, Euler/step accounting and exact ordered references.

This first selected-threshold study does not establish a universal scheduler or
justify a default-policy change by itself. Keep the feature opt-in after this
turn, even if the selected cases pass; the next decision needs broader workload
and worker-count evidence. Memory is not re-profiled in this follow-up; the
previous broad-on experiment's peak-RSS cost remains a relevant caveat, not a
new selective-gate measurement. The data-validation skill informs the controls,
independent calculations and restrained conclusion; deliverables remain code and
repository benchmark notes.

**Results:** the [completed follow-up](rk_selective_closure_benchmark.md) meets
the selected-case benefit/control criteria. The feature remains opt-in as
precommitted; only one input exercises the new path, and sequential version
warnings remain unresolved.
